## 1. Canonical Event Envelope

Every domain event written to PostgreSQL `outbox` and published to Kafka adheres strictly to the envelope specification defined in `docs/reference/settled-decisions.md`.

```json
{
  "event_id": "c7a8b941-8f20-4e2b-b6d4-83b6791e84a2",
  "event_type": "appointment.booked",
  "event_version": 1,
  "occurred_at": "2026-09-15T09:42:11.108Z",
  "producer": "swasthya-core-monolith",
  "correlation_id": "req_8df02a4e",
  "causation_id": "req_7ab19e2c",
  "actor": {
    "type": "user",
    "id": "usr_sunita_01"
  },
  "subject": {
    "type": "appointment",
    "id": "appt_gurugram_0192"
  },
  "facility_id": "fac_gurugram_phc_01",
  "payload": {
    "slot_id": "slot_gurugram_01",
    "patient_id": "pat_sunita_01",
    "department_code": "GEN_MED",
    "token_number": 19,
    "is_walk_in": false
  }
}
```

### Envelope Field Specifications

| Field | Type | Server-Derived? | Description |
|---|---|---|---|
| `event_id` | `UUIDv4` | **Yes** | Unique identifier for deduplication and ClickHouse `ReplacingMergeTree` primary key. |
| `event_type` | `string` | **Yes** | Fully-qualified event name matching the frozen topic list. |
| `event_version` | `integer` | **Yes** | Integer schema version (starts at 1) for evolving event contracts. |
| `occurred_at` | `ISO 8601 UTC` | **Yes** | Database timestamp when transaction committed (`NOW()`). |
| `producer` | `string` | **Yes** | Microservice or monolith component identifier emitting the event. |
| `correlation_id`| `string` | **Yes** | End-to-end request tracer from `X-Correlation-ID` or generated by gateway. |
| `causation_id` | `string \| null` | **Yes** | The event ID or message that directly caused this transition. |
| `actor` | `object` | **Yes** | Authenticated actor extracted from JWT claims (`{type: "user" \| "system", id}`). |
| `subject` | `object` | **Yes** | Aggregate entity type and ID (`{type: "patient" \| "appointment" \| "record", id}`). |
| `facility_id` | `string \| null` | **Yes** | Physical facility context. **Strictly derived from path/token; never client body.** |
| `payload` | `object` | **Yes** | Minimal, typed entity metadata. **Zero PII (No names, phones, or notes).** |

## 4. WebSocket vs. Kafka Streaming Architecture

```mermaid
flowchart TD
    subgraph ClientLayer ["Client Presentation Layer"]
        DoctorUI["Doctor Console (Web)"]
        PatientApp["Patient Phone (PWA / Mobile)"]
        TVBoard["Waiting Room TV Display"]
    end

    subgraph CoreMonolith ["FastAPI Monolith Transaction Boundary"]
        API["POST /queues/call-next"]
        DB[(PostgreSQL 16)]
        OutboxTable[(outbox table)]
        RedisPubSub[("Redis Pub/Sub Channel")]
    end

    subgraph AsyncBus ["Durable Event Stream (Async)"]
        OutboxWorker["Outbox Relay Worker"]
        Kafka["Apache Kafka Topic: queue.updated"]
        ClickHouse[("ClickHouse OLAP Database")]
        SMSWorker["SMS Notification Worker"]
    end

    DoctorUI -->|HTTP Request| API
    API -->|1. Atomic Commit| DB
    API -->|2. Write Event in same TX| OutboxTable
    API -->|3. Sub-millisecond Push| RedisPubSub
    RedisPubSub -->|WebSocket Push (< 3ms)| DoctorUI
    RedisPubSub -->|WebSocket Push (< 3ms)| PatientApp
    RedisPubSub -->|WebSocket Push (< 3ms)| TVBoard

    OutboxTable -->|Polled by SKIP LOCKED| OutboxWorker
    OutboxWorker -->|Batch Publish| Kafka
    Kafka --> ClickHouse
    Kafka --> SMSWorker
```

### Why WebSocket Push Never Waits on Kafka
1. **Zero Waiting Hall Latency:** When a doctor presses "Call Next", the token change must appear on the physical waiting room TV in $< 50\text{ms}$. Going through Kafka produces broker scheduling latency and consumer group polling delay ($200\text{ms} - 3000\text{ms}$).
2. **Reliability Isolation:** If Kafka brokers are restarting, rebalancing, or backlogged with batch analytics, the physical queue inside the hospital must continue without interruption.
3. **Decoupled Roles:**
   - **WebSocket via Redis:** Ephemeral, loss-tolerant, sub-second visual synchronization.
   - **Kafka via Outbox:** Durable, loss-intolerant, ordered event log for analytics and external systems.

## 5. Replay Safety & Deduplication: `ReplacingMergeTree`

When backfilling historical data or recovering from consumer crashes:
1. Every event carries an immutable `event_id` (UUIDv4) generated at the moment the outbox record was written.
2. In ClickHouse, analytical tables are defined using the `ReplacingMergeTree` engine:
   ```sql
   CREATE TABLE default.analytics_events (
       event_id UUID,
       event_type LowCardinality(String),
       facility_id String,
       occurred_at DateTime64(3, 'UTC'),
       payload String
   ) ENGINE = ReplacingMergeTree(occurred_at)
   PRIMARY KEY (event_type, facility_id, event_id)
   ORDER BY (event_type, facility_id, event_id);
   ```
3. If an event is replayed twice due to network retries, ClickHouse background merges deduplicate rows by `event_id`, preventing double-counting of hospital footfall, consultations, or stock numbers.

## 6. Audit of State-Changing Endpoints Emitting No Events

Every state-changing (`POST`, `PUT`, `DELETE`) endpoint in `endpoints.md` was inspected. The following state-changing operations emit **no domain events on the message bus**, for explicit architectural reasons:

1. `POST /auth/otp/request`: Rate-limited by Redis; emitting an event would create spam on the message bus for failed attempts.
2. `POST /auth/logout`: Ephemeral session revocation handled locally in Redis blacklist.
3. `PUT /patients/{id}`: Demographic updates (e.g. name misspelling fix) are audit-logged directly in PostgreSQL `audit_log`, but do not trigger downstream asynchronous subscribers.
4. `POST /consent/grants` & `POST /consent/grants/{id}/revoke`: Security/consent controls are checked synchronously by the query layer and audit-logged in `audit_log`; they do not fan out to Kafka.
5. `POST /records/break-glass`: Generates a synchronous high-severity `audit_log` row and immediate administrative alert via internal logger; does not route through normal analytics Kafka topic.
